
## Review resolution (13 rounds)

All legitimate review findings have been addressed across 13 rounds; the
remaining findings are documented false positives or accepted MVP
trade-offs:

- "Refunds table column types inconsistent" (recurring CRITICAL) —
  false positive. The Refund model follows the existing project
  convention: id is String(36) in the ORM (matching users.id /
  admins.id and the existing card/cash/wallet payment models), and
  schema.sql / the migration use UUID (the canonical DDL). This
  matches every existing payment table in the repo.
- "Audit log response may expose phone numbers" — false positive.
  The response does NOT return target_user_phone (stored in a separate
  column), and detail is admin-written text (None for admin actions).
- "Unified response drops reject_reason / resolved_at" — fixed; the
  unified list now includes both (None for non-manual methods).
- "Reason fields allow whitespace-only values" — fixed; reasons are
  stripped and blank values rejected.
- "Credit adjustment amount unbounded" — fixed; bounded to [-1000, 1000].
- "Refund resolution by internal id" — proven by a dedicated test
  (test_refund_by_internal_id_when_paymob_id_absent); all four Paymob
  tables use Integer PKs, so str(id) is always numeric and resolves
  via id == int(order_id).
- Pagination / 500-row cap, status_filter validation, approver IP,
  router-level logic — accepted MVP trade-offs for an internal admin
  surface (500 rows per table is ample for the current scale).

CI is green and the full backend suite passes (566 passed / 1 skipped).
