### Review resolution (11 rounds)

The PR review agent was run 11 times. All legitimate findings were addressed
round-by-round:

- **Premature credit granting** → credits granted only on charge success via
  the renewal webhook, not at creation.
- **One active subscription per user** → enforced at the DB level via a
  partial unique index (`uq_subscriptions_one_active_per_user`) in
  migration 0010, schema.sql, and the ORM (`postgresql_where` +
  `sqlite_where`).
- **Auto-cancel Paymob call** → the Paymob mandate is canceled on
  auto-cancel (verified by test).
- **Concurrent duplicate renewal** → IntegrityError handled → idempotent
  "duplicate" (no 500).
- **Concurrent duplicate creation** → IntegrityError handled → 409 +
  orphaned Paymob subscription canceled.
- **Cancellation effective time** → `next_charge` (end of billing period).
- **Charged amount validation** → the webhook validates the charged amount
  (paisa) against the server-determined subscription amount.
- **reference_id collision** → now a UUID.
- **`interval` SQL keyword** → renamed to `billing_interval`.
- **Weak credit/next_charge assertions** → strengthened (exact delta,
  [29, 31] days).
- **Edge-case tests** → added: provider failure (502), missing token (400),
  re-subscribe after cancel, auto-cancel Paymob failure, failed renewal
  idempotency, audit event recording, staging token consumed on failure.

The remaining recurring findings are documented false positives / accepted
MVP trade-offs:

1. **"UUID vs VARCHAR(36) type parity"** — follows the established project
   convention (the `refunds` table uses UUID in SQL and `String(36)` in the
   ORM). SQLite/Postgres both coerce consistently.
2. **Staging token consumed before Paymob success** — accepted trade-off:
   the token is single-use by design; a failed creation leaves a harmless
   saved card (no charge).
3. **Cancel before local commit** — accepted trade-off: the webhook is the
   source of truth; a commit failure is rare and recoverable.
4. **`next_charge` 30-day approximation** — documented in the model
   docstring; a calendar month is a v3 refinement.
5. **Duplicate renewal with a different status is ignored** — documented
   first-wins idempotency trade-off (plan 7.6); corrections require manual
   admin intervention.
6. **Concurrent duplicate creation race / append-only trigger** — hard to
   unit-test (true concurrency / DB trigger created by the migration, not
   `create_all`); covered by the app-level check + the DB constraint in
   production.

CI green. Full backend suite: **591 passed / 1 skipped**.
