## Summary

Adds a cash payment method (Fawry / bank) to the Paymob integration:
the user receives a single-use payment code with a 24 h expiry to pay
at a Fawry point or bank branch, with the app polling the payment status
until it settles.

## Backend

- `POST /payment/confirm` now accepts `method_type: "cash"` (dispatched
  alongside card/wallet on the **same** endpoint — there is no separate
  cash route).
- `_confirm_cash_payment`: validates fawry/bank, enforces 5 cash
  confirms/hour (mirrors the wallet limiter), persists the payment with
  `payment_code` + `expires_at` (24 h).
- `_update_cash_payment_status`: polls Paymob for the cash status and
  lazily expires stale `pending` payments (`canceled` + `cash_expired`
  audit).
- `GET /payment/status/{payment_id}` echoes `payment_code` + `expires_at`
  for cash payments (owner-only).

## Flutter

- `PaymentFlowScreen`: package → method (wallet | cash) →
  - **wallet**: type + number + confirm dialog + OTP (existing flow).
  - **cash**: channel (Fawry/bank) → single-use code display with copy
    button + 24 h expiry → result.
- 60 s status polling aligned to the server's 1/min limit.
- Full l10n (en + ar) for the new flow.

## Endpoint note (review verification)

The review agent repeatedly flagged a "cash confirm endpoint mismatch"
(client calls `POST /payment/confirm` while it expected
`/payment/confirm-cash`). This is a **false positive**: the backend
exposes a **single** `POST /payment/confirm` route that dispatches on
`method_type` (card / wallet / cash), and the client correctly sends
`method_type: "cash"` to that route. There is no `confirm-cash` endpoint
in the backend or in the plan. Verified against the backend route, the
client call, and `plans/paymob-cash-payments.md`.
